# 笔迹点集连续存储（安卓）

> 2026-11-28 起。只改安卓内部的内存表示；线格式（`PROTOCOL.md`）、库里的二进制列（`BINARY-INK-PLAN.md`）、Mac 端一律不动。

## 1. 为什么

Pad 6 上 301 工作区的画板：9400 条笔迹、58 万个点。原先每个点是一个 `Pt3` 对象：

- 内存：一个点约 28 字节（对象 24 + 列表里的引用 4），连续存只要 12 字节。58 万点 ≈ 16MB 对 7MB。
- 打开：从二进制列解出来要逐个新建 58 万个对象（正式包「笔迹解析」165ms）。
- 内存回收：每次都要把这些对象逐个过一遍。
- 按内容比较 / 查缓存：`Stroke` 是 data class，哈希要把全部点算一遍；`InkRenderer` 的几何缓存就是按内容查的，每画一条都算一遍。

## 2. 做法

`shared/PackedPts`：一条笔迹的点存在一个 `FloatArray` 里（x, y, p 交错），对外仍是 `List<Pt3>`。

- **现有代码不用改**：取一个点临时建一个 `Pt3`，用完即弃。
- **热路径直接读数**：判 `is PackedPts` 后用 `x(i)` / `y(i)` / `raw()`，不建对象。
- **比较与哈希**：`equals` / `hashCode` 与同样内容的 `ArrayList<Pt3>` 完全一致（List 契约 + `Pt3` data class 的算法），两种混在一起比结果不变；哈希算一次就缓存。
- 🔴 只读：建好后不许改底下的数组。

## 3. 分批

| 批 | 内容 | 状态 |
|---|---|---|
| 1 | `PackedPts` 本身；`InkPointsBlob.decode` 整块解成它（含分页偏移）、`encode` 直接写；新写的画板笔迹（`BoardController.commitInk`）存成它；包围盒（`ScratchTiles.box`）、内容范围（`ScratchGeom.contentBounds`）直接读数。测试 `PackedPtsTest` | 已实测（2026-11-28） |
| 2 | 渲染：`InkRenderer` 建几何前一次换算成数组（`mapped`：原始 x/y、屏幕 x/y、压感），四种笔型的循环只读数组、不再经装箱的映射函数；分块位图后台画笔迹走同一条路 | 已实测（2026-11-28：观感不变；视口出齐 16~51ms，提升有限——大头是系统的描边转轮廓） |
| 3 | 命中与编辑：整条擦除命中（`ScratchCanvas.eraseAt`）直接读数；`InkEdit.splitStroke` 遇 `PackedPts` 整块切段；框选命中 / 选中范围直接读数，框选平移 / 缩放（`PackedPts.translated` / `scaled`）直接产出。测试 `PackedPtsTest` 与原算法逐点比 | 已实测（2026-11-28：框选判定 1~2ms / 9733 条，擦除增量写库 2~12ms） |
| 4 | 其余：页内笔迹（`LocalCanvasView` / `PageCanvasView`）、模式2 解码（`WireCodec`）、剪贴板 | 暂不做（PDF 页上笔迹少、收益小，且要碰线格式解码；页内笔迹也多到卡了再做） |

每批单独可验：JVM 单测 + 真机看 `UniReader/BoardPerf`（打开画板的「笔迹解析」、整表替换、出帧）。

## 4. 验收数字（Pad 6，正式包，301 工作区画板）

| 项 | 改之前 | 批 1 后 |
|---|---|---|
| 打开画板：笔迹解析 | 137~165ms | 105~117ms |
| 打开画板：查库 | 239~275ms | 不变（SQLite 搬数据，本方案不管） |

## 5. 不做的

- 不换原生（C/C++）实现：数据在 Kotlin 对象里，来回搬运比计算还贵；真正费力的画线（Skia）、存库（SQLite）本来就是原生的。
- 不改跨端格式：点的二进制格式、线格式、JSON 兼容规则都不动。
